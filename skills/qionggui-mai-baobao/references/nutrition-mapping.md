# 菜单名 ↔ 营养表名 对照表

## 为什么需要这张表

麦当劳有两套独立的数据源：

- **`query-meals`** 返回的是**售卖名**（菜单上印的名字）
- **`list-nutrition-foods`** 返回的是**营养成分表名**

两者的命名规则不同，直接按字符串相等去匹配，命中率大约只有 70%。
本 Skill 用「归一化 + 别名 + 双向包含」三级匹配，把命中率提到 95%+。

## 归一化规则

`normalize_name()` 依次执行：

| 步骤 | 输入 | 输出 |
| --- | --- | --- |
| 去首尾空白 | `" 巨无霸 "` | `"巨无霸"` |
| 全角转半角 | `"ＡＢＣ"` | `"abc"` |
| 去括号补充说明 | `"纯牛奶（盒装）"` | `"纯牛奶"` |
| 去空白与连字符 | `"麦乐鸡 5块"` | `"麦乐鸡5块"` |
| 转小写 | `"BigMac"` | `"bigmac"` |

## 别名映射（`NUTRITION_ALIASES`）

只登记**两表命名确实不同**的商品。若两表同名（如「麦辣鸡腿汉堡」），
归一化后会直接 exact 命中，**不要**在这里重复登记——
否则会让本该 exact 的查询误走 alias 路径。

| 售卖名 | 营养表名 | 备注 |
| --- | --- | --- |
| 板烧鸡腿堡 | 原味板烧鸡腿麦香鸡 | 菜单简称 |

## 常见陷阱

### 陷阱 1：同名误配为别名

```
❌ NUTRITION_ALIASES = {"麦辣鸡腿堡": "麦辣鸡腿汉堡"}
```

若营养表里本来就有「麦辣鸡腿汉堡」，归一化后 `麦辣鸡腿堡` 与
`麦辣鸡腿汉堡` 仍是两个不同的 key，所以这条映射看起来"有用"。
但一旦营养表某天补上了「麦辣鸡腿堡」这条记录，这条映射就会
**劫持**本该 exact 的查询。

**处理**：只在确认两表命名不同时才登记。

### 陷阱 2：双向包含的过度匹配

`lookup_kcal` 的最后一级是双向子串包含：

```
"巨无霸套餐".find("巨无霸") → 命中
"可乐中杯".find("可乐") → 命中
```

这可能出现误配，例如「麦辣鸡翅」和「麦辣鸡腿汉堡」都含「麦辣」。
因此实现里加了**长度差最小**的择优规则：

```python
diff = abs(len(k) - len(key))
if best is None or diff < best[0]:
    best = (diff, v)
```

### 陷阱 3：套餐热量被重复计算

套餐名若同时命中了整体和子项，必须**只取一条路径**：

```python
def _combo_kcal(name, meal, nutrition):
    kcal, hit = lookup_kcal(name, nutrition)
    if hit in ("exact", "alias"):
        return kcal          # ← 整名命中即返回，不再叠加子项
    # 只有整名未命中时，才逐个子项求和
    ...
```

## 未收录商品的处理

若某商品在营养表里完全查不到，返回 `(0, "miss")`：

- 热量按 0 计（**不会**用估算值污染最优解）
- 商品名会被记入 `warnings`，在输出的第一份方案下方提示用户

这是刻意的保守设计：**宁可漏掉一个高热量商品，也不要编造一个假数值**
误导用户的决策。

## 扩展这张表

发现新的未匹配商品时：

1. 在 `nutrition.txt` 里搜索该商品的营养表名；
2. 若命名确实不同，在 `NUTRITION_ALIASES` 里加一行；
3. 跑 `tests/test_solver.py` 确认没破坏既有断言；
4. 若营养表里根本没有该商品，属于**数据缺失**，不要臆造数值。
